## My Choices and Why
- **Model Choice: `qwen/qwen3.8-27b`**: `llama-3.1-8b-instant` returned 404 (model not found on current API account). Among available chat models, `qwen/qwen3.8-27b` provides direct, non-reasoning token generation with zero wasted reasoning tokens, high instruction adherence, native streaming support, and fast response times.
- **Empirical Rate Limit Confirmation**:
  - `x-ratelimit-limit-tokens: 8000`: This is 8,000 Tokens Per Minute (TPM), resetting continuously (measured reset: 127–134ms).
  - `x-ratelimit-limit-requests: 1000`: Response headers revealed `x-ratelimit-reset-requests: 7m12s`, proving that the 1,000 limit is a daily/rolling quota (RPD), NOT 1,000 RPM.
  - **TPM is the True Chokepoint**: With an average retrieval context of ~2,000 tokens, 3 to 4 concurrent or closely-spaced requests immediately exhaust the 8,000 TPM limit.
- **Dual Timing Representation**:
  - `results.csv`: `first_token_ms` represents the **user-visible time-to-first-token** (emitted to the user after draft completion and deterministic verification), strictly complying with the brief's required schema.
  - `timings_detail.csv`: Logs the fine-grained attempt breakdown including `raw_model_ttft_ms` (time when model first emitted tokens), `headers_received_ms`, `verification_ms`, and `sleep_before_retry_ms`.
- **Stand-in Model Assumptions & Limitations**:
  - Concurrency penalty ($1.25^{\text{in\_flight}-1}$) is an explicit synthetic assumption representing thread queueing backpressure; real Groq datacenter latency jumps discontinuously based on multi-tenant traffic.
  - Latency is scaled continuously by token volume: ~0.12 ms per input token (prefill) + ~7.5 ms per output token (decode), derived from empirical probe measurements.
- **Dynamic Header Pacing**: Pacing retrieval experiments based on `x-ratelimit-remaining-tokens` and `x-ratelimit-reset-tokens` headers rather than static sleeps ensures the pipeline stays below the 8,000 TPM limit (~3.0 requests/min capacity).
- **Verifier Scope and Limitations**: The deterministic verifier checks citation syntax, valid paper versions, valid page boundaries, presence of cited page in retrieved context, and lexical overlap. It does **not** prove ground truth or semantic validity.
- **Deadlined Queue Over Hard 503 Drop**: When rate limits or concurrency caps are reached, requests are placed in an in-memory queue with an expiration deadline and an informative retry message if the deadline is exceeded.
- **Synthetic Daily Exhaustion in Stand-in**: To test the daily exhaustion scenario without consuming the user's real daily quota, the stand-in model server simulates a configurable daily token/request budget cap.

## Measurements That Contradicted Assumptions
1. **Model Availability**: Assumed `llama-3.1-8b-instant` would be accessible on all Groq accounts. Live API call returned `404 Not Found`; `qwen/qwen3.8-27b` was measured and confirmed functional instead.
2. **Requests Per Minute vs Daily Quota**: Assumed `x-ratelimit-limit-requests: 1000` represented 1,000 RPM. However, the accompanying header `x-ratelimit-reset-requests: 37m26.4s` disproved this: 1,000 is a daily/rolling window limit (RPD), with a refill rate of 86.4 seconds per request ($86,400\text{ s} / 1000 = 86.4\text{ s}$), whereas tokens reset on a sub-second scale (`134ms`) under an 8,000 TPM limit.
3. **The Hidden OTPM Limit Contradicts "TPM is Binding"**: While we initially assumed total TPM (8,000) was the primary constraint, the raw 429 error body proved that **Output Tokens Per Minute (OTPM) has a hard cap of 1,000 tokens**. Under burst requests, 429 fired with 7,005 total tokens still remaining because cumulative output tokens hit 970/1000 and the requested `max_tokens` exceeded the remaining OTPM allowance.
4. **The 500k TPD Assumption and 250k Cap Were Wrong**: We initially assumed a 500k tokens/day limit from general developer documentation and planned a ~250k token cap. A live HTTP 429 error body explicitly contradicted this: `Limit 200000, Used 199180, Requested 2032`. The true on-demand daily ceiling for Qwen 27B is **200,000 tokens/day**, and our planned 250k cap was physically impossible on this tier.
5. **Daily Limit is a Rolling Leaky Bucket, Not a Midnight Reset**: The 429 error stated 1,212 excess tokens needed ($199,180 + 2,032 - 200,000 = 1,212$) with a retry-after of `523.584 s` (`8m43.584s`). Exactly $1,212 \times (86,400\text{ s} / 200,000\text{ tokens}) = 1,212 \times 0.432\text{ s} = 523.584\text{ s}$. The daily quota refills continuously at ~2.31 tokens/second (0.432 s/token), rather than resetting in a discrete batch at midnight UTC.
6. **True Server-Side Latency vs Silent Client Retries**: The previous assumption that "99.9% of delay is inside Groq's queue" was disproven. Instrumenting with `max_retries=0` and attempt-level logging revealed that true server model TTFT is **438.1 ms** (p50) and **1,439.8 ms** (p95). The ~7s-12s spikes were client backoff sleeps ($2.4\text{s} + 4.2\text{s}$) triggered when consecutive full-context requests hit the 8,000 TPM boundary.
7. **Thundering Herd Collision on Retry-After**: Retrying blindly without jitter after the exact `retry-after` header delay caused a 50% collision rate across 3 trials (6 of 12 parallel requests hit 429 again) due to synchronized token requests re-saturating OTPM at the identical millisecond.
8. **In-Flight Concurrency Tested**: Firing 4 simultaneous requests with low token requests succeeded concurrently in ~210ms, confirming no restrictive in-flight concurrency throttle $\le 4$.
9. **Fast 429 Edge Rejections Dragging Down Median Latency**: In burst and sustained overload scenarios, unserved requests received fast HTTP 429 edge rejections (~25-35 ms) from the stand-in before timing out at the patience deadline. Calculating percentiles across all requests artificially pulled down the median (`p50`) to ~35 ms; isolating `status=ok` rows restored the true generation latency (~580 ms TTFT, ~880 ms total).
10. **Q3 Facts Split Across Non-Contiguous Pages**: Expected answers initially cited only Page 11 and Page 24 for Moshi latency and codec parameters. Verification proved that the 160ms/200ms latency is explicitly stated on Page 1 (Abstract) and Page 2 (Section 1), while the 12.5 Hz / 1.1 kbps Mimi parameters appear on Page 11 and Page 23.
11. **Bibliography Bleed in Naive Retrieval**: BM25 matching repeatedly retrieved reference lists (e.g. Moshi citing Attention Is All You Need; Dynamic Chunking citing ImageNet and ResNet) with higher keyword density than the true content passages, causing false positive context inclusion until bibliography sections were excluded.
12. **Retries Accounting Audit (Attempts Minus 1)**: Auditing identified that `pipeline.py` previously incremented `retries += 1` on attempt 0 prior to deadline timeouts. Correcting `pipeline.py` to count only secondary attempts ($attempt > 0$) and recomputing all rows in `results.csv` from `timings_detail.csv` brought `burst`/`overload`/`limit_halved` retries from ~0.6 to 0.0, and `probe_pipeline` from 1.33 to 1.00 retries/req.
13. **TPD Leaky-Bucket Confirmation**: Groq's daily limit was verified to be a continuous rolling leaky-bucket refilling at ~2.3 tokens/s (86,400s / 200,000 tokens = 0.432 s/token) rather than a midnight UTC reset.
